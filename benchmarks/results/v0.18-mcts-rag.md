# V0.18 B 部分：MCTS-RAG（dev）

设计与接口见 `docs/research/mcts-rag.md`，代码在 `treeengine/mctsrag`。

**评测设置**

- 题目：只用 dev 集，共 78 题（FinanceBench 35 / multires2 20 / longdoc 23）。
- 预算：每题 2000 token。
- 所有方案的初始候选都相同，来自 `policy_gate@rerank=MiniLM`。
- 逐题明细：`v0.18-dev-b-{fb,m2,ld}.md`。

**MCTS-RAG 的动作**

| 类别 | 动作 |
|---|---|
| 检索 | SEARCH_BM25 / SEARCH_VECTOR / SEARCH_TREE / SEARCH_FUSED（对问题、子问题、改写后的查询） |
| 证据扩展 | EXPAND（价值最高的块的邻块） |
| LLM 思考 | THINK_DECOMPOSE（拆问题）、THINK_VERIFY（判断能否作答 / 覆盖率 / 缺什么，并据此生成改写查询） |

**搜索方式**

- 状态价值：对问题和每个子问题，取候选池中 cross-encoder 分数的最大值，经 sigmoid 后加权；做过 VERIFY 的节点再混入 LLM 判断的覆盖率；每多一个动作扣一点成本。
- 选择：UCT 加动作先验。不做 rollout，直接用叶子节点的估值。
- 默认参数：24 次迭代，深度 4，THINK 调用最多 2 次。
- 读取：搜索结束后，取价值最高状态的候选池，用置信门控读一次；答案层面的 retry 保留。

## 2. MCTS 实际选了什么

最终选中的状态（从根节点出发的路径）分布如下。只统计记录了搜索路径的题，重试过的题有一部分没有这条记录：

| 题集 | 默认版 | `llm=0` 版 |
|---|---|---|
| FinanceBench | 根节点 13 题，VERIFY 8 题，VERIFY→DECOMPOSE 2 题，DECOMPOSE→检索 2 题 | 根节点 25 题 |
| multires2 | 根节点 13 题，DECOMPOSE 3 题，其余为 VERIFY | 根节点 18 题 |
| longdoc | 根节点 12 题，VERIFY 5 题，DECOMPOSE 3 题 | 根节点 20 题 |

最终候选池平均 48–49 个块，和初始种子差不多。

## 3. 结论

1. **MCTS-RAG 没有胜过参照**（82.1 对 84.6，3:5，差异不显著），LLM 调用却多了 2.5 倍，延迟 p50 从 3 秒涨到 18 秒。
   - 不调 LLM 的版本和参照打平（83.3，2:3）：它几乎总是停在根节点，等价于"种子候选 + gate 读取 + retry"，也就是参照本身。
   - 不过它比 V0.17 的 Tree-RAG 明显好（74.4，参照对 Tree-RAG 9:1，p=0.02）。原因是 MCTS-RAG 不按子问题切分预算，最后统一用一次 gate 读取。
2. **瓶颈在价值函数，不在搜索算法。**
   - 种子是 50 个融合候选，对原问题来说，"最好的 cross-encoder 分数"几乎已经饱和。再做 BM25、向量或树检索，往候选池里加进来的块很难把这个最大值再抬高；而每多一步都要扣成本，所以搜索的最优解经常就是"什么都不做"。
   - 真正让价值变化的，只有 LLM 的 VERIFY：答案可回答时，覆盖率被抬到 ≥ 0.9。但 VERIFY 本身不带来新证据，只是确认现有证据。
   - 这和 V0.16 / V0.17 的结论一样：在这些单文档、找数字的题上，MS MARCO 训练出的小 reranker 当价值函数不够准，搜索越细收益越小。
3. **DECOMPOSE 很少出现在最优路径上**（至少 13 题），这些题的对错没有单独分析。

## 4. 下一步（不在本轮做；按 held-out 纪律，这一轮也不送 held-out）

- **换价值函数**：
  - 用 dev 上拟合的"答对概率"模型（gate 的置信特征加 reranker 特征）替代"最大 CE 分数"；
  - 或者把价值定义为对每个子事实（数字 / 年份 / 项目）的覆盖，而不是整题的相关度。
- **把 LLM 判断放到能产出新证据的地方**：VERIFY 给出的 missing 查询，只有在后续迭代里被展开才会真正去检索。可以改成 VERIFY 之后强制展开改写分支，或者把 gate 的选读本身当作 MCTS 的一个动作。
- **需要专门的多跳 / 跨文档题集**：在现有三个 dev 集上，参照已经很接近天花板（multires2 95–100，longdoc 87）。

## 5. 局限

- 回答模型有随机性：同一参照配置在两次运行中的 FinanceBench 结果分别是 65.7 和 77.1。表中的比较全部是同一次运行内的逐题配对比较。
- 只跑了一轮，参数用的是默认值，没有调。
