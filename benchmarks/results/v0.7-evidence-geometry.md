# V0.7 — Evidence Geometry / Structure Geometry 解耦

按《TreeEngine V0.7 — Evidence Geometry / Structure Geometry 解耦执行计划》执行。

## 改了什么

```text
Source -> Adapter -> canonical Document (text + offsets, PDF: + page offsets)
                       |-- EvidenceBuilder  -> stable Blocks   (FTS / Vector)
                       `-- StructureBuilder -> Tree Nodes      (boundaries / navigation)
                     Block -> Node mapping by offset overlap  -> Repository
```

- **`treeengine/blocks/builder.py`：`EvidenceBuilder`**，只从 canonical text 生成 Block。
  - Markdown / HTML：沿用源格式解析出的段落、列表、表格、代码、引用（和以前完全一致）。
  - PDF：按空行、换页、以句号结尾的短行、900 字符上限切段，切出来就是 V0.4 验证过的 flat 段落，也是之前最强的 FTS baseline。不使用任何标题规则，标题行留在所在段落里，不丢任何文本。
  - 超长 Block 按 `max_block_chars` 再切。
  - Block ID = sha1(document_id + start + end + 内容哈希)，不含 node、深度或标题。
- **`treeengine/blocks/mapping.py`**：按 offset 把 Block 映射到 Node。
  - 节点的 *own range* = 节点范围中第一个子节点之前的部分。所有节点的 own range 互不重叠，覆盖整篇文本。
  - 每个 Block 的主节点 = own range 与它重叠最多的节点，平局取更深的。
  - 跨多个节点的 Block 额外记录 `metadata["node_ids"]` / `["node_overlap"]`。
  - 第一个章节之前的文本，给一个 preamble 节点。
  - 映射不会重新切 Block。
- **`StructureBuilder.build_tree`** 只产出带 offset 的节点；**`finalise`** 用映射后的 Block 填节点的正文、页码和摘要。由 `pipeline.build_document` 把两边串起来。`StructureBuilder.build` 保留为兼容入口。
- **公共工具**：PDF 文本工具（页码查找、分行、页眉页脚）从 `structure/pdf.py` 移到 `ingest/pdf_text.py`，两个 Builder 都只依赖它。
- **配置**：
  - `EngineConfig.evidence_geometry = "stable"`（默认）。设成 `"coupled"` 就是 V0.7 之前的行为，A/B 实验用它。
  - `EngineConfig.index_title = "document"`（默认，见下文）。设成 `"section"` 时，FTS 标题列和向量前缀用节点标题。
- **公开 API 不变**：`engine.search / retrieve`、`RetrievalPolicy`、`Evidence`、`ContextSpan`、Repository 协议都没改，schema 也没有迁移，`Block.node_id` 仍是主归属。
- **计划之外的一处改动：索引标题。**
  - 以前 FTS 的 title 列和向量前缀是节点标题，Tree 一变，检索语料还是会变，Invariant 1 不成立。
  - 现在 stable Block 把 `metadata["index_title"]` 设为文档标题；FTS（包括重建）和 VectorIndexer 优先读它。重命名节点也不会改 FTS。
  - 有两个旧的 tree 导航回归测试，它们的启发式依赖 FTS 里的章节标题，已固定为 `index_title="section"`，测试里写了原因。

测试：新增 `tests/test_evidence_geometry.py`（17 个），全部 174 个测试通过，ruff / mypy 干净。冻结：retrieval `ac9e9bf10ee7f7ae` 起，`blocks/` 和 `pipeline.py` 计入 retrieval 指纹。

## Q1. Tree strategy 改变时，Block corpus 是否稳定？是：完全一致

**FinanceBench**（33 份 10-K，`v0.7-structure-financebench-{stable,coupled}.md`）：

| 结构 | 解耦前 Block 数 | 与 flat 的 Block 重合 | 解耦前 FTS 标题数 | **解耦后 Block 数** | **重合** | **FTS 标题数** |
|---|---|---|---|---|---|---|
| flat | 39,587 | 100% | 33 | 39,587 | 100% | 33 |
| auto | 40,299 | 88.9% | 1,227 | 39,587 | 100% | 33 |
| layout | 41,097 | 79.5% | 3,432 | 39,587 | 100% | 33 |
| hybrid | 40,750 | 81.2% | 3,069 | 39,587 | 100% | 33 |
| reference | 39,867 | 94.2% | 478 | 39,587 | 100% | 33 |

解耦后，五种 Tree 下的语料哈希都是 `263b44b98526`。

**18 份真实 PDF 回归集**（`v0.7-pdf-regression.md`）：auto / layout / hybrid 三种模式下 Block 语料全部相同。另外检查通过：不崩溃、文本不丢、Block 唯一、有序、offset 单调不重叠、每个 Block 都映射到一个有效节点、section 上下文不越出所在节点和文档、无文本层的 PDF 正常入库。

**Markdown / HTML**：Block 文本、offset，以及映射到的章节都和解耦前完全一致（单元测试逐个核对 4 个 fixture）。

## Q2. 全局检索还会被结构切分拖累吗？不会了

**FinanceBench**，同样 55 题，只换 Tree：

| 结构 | FTS R@5 解耦前 → 后 | FTS R@2k 解耦前 → 后 | tree_lexical+fts R@5 前 → 后 | R@2k 前 → 后 |
|---|---|---|---|---|
| flat | 24.5 → 24.5 | 43.6 → 43.6 | 24.5 → 24.5 | 43.6 → 43.6 |
| auto | 19.1 → **24.5** | 30.0 → **43.6** | 16.4 → **22.7** | 28.2 → **35.5** |
| layout | 14.5 → **24.5** | 27.3 → **43.6** | 13.6 → 16.4 | 19.1 → 20.0 |
| hybrid | 16.4 → **24.5** | 34.5 → **43.6** | 17.3 → 19.1 | 23.6 → 22.7 |
| reference | 18.2 → **24.5** | 29.1 → **43.6** | 23.6 → **30.9** | 29.1 → **38.2** |

- 全局 FTS 不再随 Tree 变化，并且等于之前最好的 flat 基线。
- Tree scope 本身也变好了：reference 上 tree_structure 的 R@5 从 31.8 升到 40.0。这说明 V0.4 发现的 “结构伤害 FTS” 主要来自耦合切分，而不是树本身。

**longdoc**（91 题，fastembed bge-small，`v0.7-retrieval-longdoc-*.md`）：

| 配置 | FTS R@5 / R@2k | Vector R@5 / R@2k | FTS+Vector R@5 / R@2k |
|---|---|---|---|
| A 解耦前（coupled） | 65.4 / 80.8 | 69.6 / 83.7 | 71.1 / 84.8 |
| **B 解耦后（默认：文档标题）** | 65.0 / 81.1 | 60.6 / 81.7 | 66.8 / 83.2 |
| B′ 解耦后 + 章节标题（`index_title=section`） | 68.1 / 80.8 | 65.8 / 84.8 | 68.9 / 84.8 |

- B 对 A 的配对检验：FTS R@5 4:4，Vector R@5 5:13（p=0.096），FTS+Vector R@5 3:9（p=0.15）、R@2k 0:2，都不显著。
- B′ 对 A：都在 0–4 题以内。
- 解耦本身（A → B′）在 longdoc 上不影响检索。Vector 的下降来自 “索引不再带章节标题”。
- 但在 FinanceBench 上，带章节标题会把 Tree 依赖带回检索：FTS 随 Tree 在 R@5 21.8–25.5、R@2k 37.3–43.6 之间变化（`v0.7-structure-financebench-stable-section-title.md`），最好的也不超过文档标题版本的 43.6。
- **所以默认 `index_title="document"`**：它满足 Invariant 1，在 FinanceBench 上不差于任何章节标题变体；longdoc 上 Vector 的下降不显著，QA 也不受影响（见 Q4）。`section` 保留为可选项，适合章节标题本身信息量大的语料。

**被删掉的第一版**（`v0.7-structure-financebench-titleline-rule.md`）：第一版在 “像标题的短行” 处另起一个 Block，FinanceBench 的 FTS 降到 19.1 / 39.1。这条规则违反了计划 §6，已经删掉。现在的 Block 就是 flat 段落。

## Q3. Tree 还能为 ContextBuilder 提供有效的 section 边界吗？能

- ContextBuilder 没有改。section 边界 = 映射得到的主节点。映射是按 offset 几何计算的，同一节点的 Block 不再假定是 Tree 切出来的连续片段。
- 回归集里 18 份 PDF × 3 种模式，抽样检查 section600 上下文，全部不越出所在节点和文档。
- longdoc section600 QA（2 轮平均）：

| | @1000 QA | coverage | spans | avg span tok | @2000 QA | coverage |
|---|---|---|---|---|---|---|
| A 解耦前 | 62.1 | 71.1 | 2.5 | 541 | 64.8 | 79.1 |
| B 解耦后 | 58.8 | 69.2 | 2.2 | 542 | 64.8 | 74.2 |

  配对检验：@1000 为 5:10（p=0.30），@2000 为 5:6，都不显著。
- span 长度不变，说明节点边界仍然能把扩展停住。
- @1000 方向偏负（−3.3）。可能的原因是：A 的 Block 本来就在标题处断开，段落和章节完全对齐；B 的段落可能跨过标题，这时只按多数归属判断。目前不显著，记录下来，后续可以用 FinanceBench QA 复核。

## Q4. 解耦后 QA 不退化吗？不退化

longdoc，fts+vector，`auto` 上下文，两轮平均（`v0.7-qa-longdoc-*-run{1,2}.md`）：

| 配置 | QA @2000 | QA @3000 | candidate recall | coverage @2000 / @3000 | spans @3000 | section crossings @3000 |
|---|---|---|---|---|---|---|
| A 解耦前 | 65.9 | 69.8 | 96.2 | 75.8 / 77.1 | 3.1 | 5.84 |
| **B 解耦后（默认）** | **68.7** | **69.2** | 95.1 | 70.3 / 73.8 | 3.2 | 4.41 |
| B′ + 章节标题 | 69.8 | 67.6 | 95.1 | 74.7 / 76.0 | 3.1 | 4.64 |
| 传统 RAG（对照，与几何无关） | 58.2–58.8 | 58.8–59.9 | 96.7 | 69.2 / 77.5 | – | – |

- B 对 A：@2000 为 6:3（p=0.51），@3000 为 4:4。B′ 对 A：6:2 和 3:5。都不显著。
- 传统 RAG 在三种配置下都在 57–62 之间，作为对照，说明答题噪声在 ±2 点左右。
- B 的 coverage 低 4–5 点，但 QA 持平或略高；section crossings 也更少（5.84 → 4.41）。

## FinanceBench 全集（150 题，84 份文档）

按决定：B 跑完整检索 + QA；A（coupled）只跑 FTS，不算向量（A 的块标题不同，要重算约 8 万条 embedding）。报告：`v0.7-retrieval-financebench-{stable,coupled-fts}.md`、`v0.7-qa-financebench-stable-run{1,2}.md`。

**检索**（B = 解耦后，默认配置）

| 策略 | R@5 | R@2k evidence tokens |
|---|---|---|
| FTS（A 解耦前） | 34.7 | 46.0 |
| **FTS（B 解耦后）** | 34.7 | **51.7** |

**QA**（B，两次运行的平均，`auto` 上下文）

| 策略 | QA @2000 | QA @3000 | candidate recall | coverage @2000 / @3000 |
|---|---|---|---|---|
| **block_hybrid（FTS+Vector）** | **39.3** | **43.3** | 80.9 | 52.3 / 57.7 |

- 没有 A 的向量和 QA，所以这里不能直接回答 FinanceBench 上的 “Q4 解耦前后 QA 对比”。能确定的是：在相同预算下，解耦后的 FTS 召回显著更好（R@2k p=0.049），而 QA 结论在 longdoc 上已经确认不退化。

## 结论

- 四个问题都得到回答：Block 语料与 Tree 完全解耦（Q1）；全局检索不再受结构切分拖累，FinanceBench 上 auto / layout / hybrid / reference 的 FTS 都回到最好的 flat 水平（Q2）；section 边界仍然可用（Q3）；QA 不退化（Q4）。
- 默认值：`evidence_geometry="stable"`，`index_title="document"`。
- 局限：
  - FinanceBench 上只跑了 B 的 QA（A 没算向量），所以 FinanceBench 上的解耦前后 QA 对比缺失；B 对传统 RAG 在 @3000 上显著领先（22:7，p=0.008）。
  - Embedding 是临时的 bge-small，Judge 和 Answer 是同一个模型。
  - section600 @1000 方向偏负（不显著），需要复核。
