# V0.6 Agentic Retrieval Policy — longdoc（91 题 × 2 次运行）

- 运行：`run_qa --suite longdoc --preset agentic --llm --context auto --budget 2000,3000`，跑 2 次；传统 RAG 基线 `--strategies rag_hybrid` 也跑 2 次（`v0.6-agentic-rag-run{1,2}.md`）。
- 模型：Answer / Judge / 树推理都用 deepseek-flash（关闭 thinking）；Embedding 用 fastembed `BAAI/bge-small-en-v1.5`（临时，BGE-M3 还没跑）。
- 设置：ContextBuilder 固定为 `auto`，候选池 50，只换 Controller（RetrievalPolicy）。
- 准确率：correct = 1，partial = 0.5；n = 91 题 × 2 次。配对检验在题目级别做，每题先取两次运行的均值，再做双侧符号检验。
- 原始报告：`v0.6-agentic-longdoc-run{1,2}.md`。agentic run 里的 `rag_hybrid` 行无效：当时 run_qa 有 bug，chunk 策略在 `--context auto` 下没有截断预算，把全部 50 个 chunk 都给了模型，约 18.5k token。这个 bug 已修复，基线改用单独重跑的结果。

## 结论

1. **补回证据：基本没有。** 候选池（50）在 FTS + Vector 下的 recall 已经是 96%，树推理没有带来一条新的候选证据。full 模式只在 4 题上把已有证据挪进了上下文，coverage 提高 2–3 个点，但准确率没有显著变化（3:4 和 3:2）。
2. **只用 LLM 导航（类 PageIndex 的 vectorless 检索）明显更差**：准确率低 20 个点，candidate recall 只有 50%，检索 p50 为 1.6 s，每题约 2.7k token。这验证了设计里 “Tree 管导航和阅读几何，证据检索交给 FTS / Vector” 的分工。
3. **默认值：`policy_hybrid`，agentic off。** fallback / guided 只在约三分之一的题上触发（判定为证据不足），不增加延迟，但也没有可测的收益；full 让检索延迟上升约 100 倍（31 ms → 2.9 s），收益不显著。agentic 作为可选能力保留，适合证据分散、检索词与原文不匹配的场景，这类场景需要专门的数据集来验证。
4. **对比传统 RAG 复现了 V0.5 的结论**：policy_hybrid 比 rag_hybrid 高 8–9 个点（@2000：p=0.049）。收益来自阅读单元重建（auto context），不来自 agentic。
5. 局限：只有一个数据集（longdoc，91 题），Embedding 是临时的，Judge 和 Answer 是同一个模型。
