# V0.10 — Retrieval Tree 与自适应阅读粒度

架构说明见 `docs/v0.10-retrieval-tree.md`。快路径信号都一样（FTS + bge-small 向量），QA 由 DeepSeek 作答并判分，每个配置独立跑两轮。

- **开发集 longdoc**（91 题）：设计在这里迭代。
- **留出集 FinanceBench**（150 题，hybrid 结构）：设计定稿后只跑一次，没有据它修改设计。

对比的策略：

- `policy_hybrid` / `block_hybrid:auto`：基线。FTS + 向量做 RRF 融合，用 auto 上下文。
- `rtree_hybrid`：检索树（`fusion="tree"`），带节点信号（标题 BM25 和子树质心）。
- `rtree_hybrid_nonode`：检索树，不带节点信号，只做块信号的向上传播加自适应停止。
- `block_hybrid:resolution`：检索不变，只把上下文策略换成 `resolution`。

## 结论

- **整体不显著，但方向分化。**
  - 留出集 FinanceBench 上，三个新方案在 @1000 和 @2000 都高于基线，提升 1.5–4 分。其中 resolution @1000 是 8:1（p=0.04），rtree 无节点信号 @2000 是 21:10（p=0.07）。
  - 开发集 longdoc 上，三个方案都持平或略低。
  - 一共做了 16 次检验；按四个配置合并后，p 都在 0.18 以上。所以结论是：**没有证据表明 V0.10 比 V0.9 默认方案更好，也没有证据表明更差。**
- **数据集差异的一种解释**：
  - FinanceBench 是 10-K，答案常散在同一节的表格和正文里，比如「某项费用变化的原因」，读整节有机会把分散的证据一起带进来。
  - longdoc 多为单点查找，读整节会占掉其他命中的位置；@1000 时上下文覆盖率下降 2–3 点。
  - 这个解释符合设计初衷，但目前的数据不足以证实它。
- **节点信号（标题 BM25 + 子树质心）没有贡献**：两个数据集上都不显著，FinanceBench @2000 上还略差。真正起作用的是块信号的向上传播加自适应停止，节点信号目前只增加了复杂度。
- **噪声提醒**：同一份基线代码两轮之间相差可达 3.4 分（FinanceBench @2000：37.3 / 40.7），单轮差异不能当真。
- **成本**：检索树不调用 LLM，单篇文档的检索耗时从 6.4ms 增加到 8.5ms。节点索引第一次构建需要读取全部块向量，之后走缓存。

## 建议

- 默认保持 `fusion="rrf"` 和 `context_policy="auto"`。
- `fusion="tree"` 和 `context_policy="resolution"` 作为可选项保留，适合财报这类证据成段分布的长文档，有 FinanceBench 的正向信号支持。
- 要下结论，需要一个独立的「证据跨块但在同一节内」的问题集，或者更多轮次的 FinanceBench 运行，而不是回到 longdoc 调参。
- 节点信号默认值是否改为 0：建议在新数据上验证后再决定，不在这里调。

## 开发过程（longdoc，记录在案）

1. resolution 第一版用全局「单位 token 价值」贪心，上下文覆盖率掉了 10–14 点：排名质量太平，便宜的低排名单元挤掉了第一名。
2. 改为按排名顺序做局部比值比较后，窗口永远赢，整节从来没被选中。
3. 最终采用机会成本判据，覆盖率与 auto 持平。
4. rtree 的「强证据」最初按「≥ 0.5 × 最强块」的比例定义，所有块都过线；后来改为按排名定义，即激活值前 10 的块。
