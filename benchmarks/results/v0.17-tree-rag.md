# V0.17 — Tree-RAG（Query Tree + Retrieval Search Tree + Evidence Tree）dev 评测

设计与接口见 `docs/v0.17-tree-rag.md`。本轮只在 dev 上评测：FinanceBench 35 题、multires2 20 题、longdoc 23 题，共 78 题，各跑 1 轮，每题预算 2000 token。

- 所有方案共用同一检索策略 `policy_gate@rerank=MiniLM`，回答模型和判分也相同。
- 参照是 V0.16 在 held-out 上的最优方案：reranker 特征 + gate + retry。
- 胜:负 为逐题对参照的比较；LLM 调用只算检索侧，回答那一次不计在内。

## 1. 结果

| 方案 | FinanceBench | multires2 | longdoc | **合计准确率** | **对参照 胜:负** | 每题 LLM 调用 |
|---|---|---|---|---|---|---|
| **参照：reranker 特征 + gate + retry（V0.16）** | **74.3** | **100.0** | 87.0 | **84.6** | — | 1.31 |
| Tree-RAG，gate 叶子读法，不拆问题（`rd=gate;dec=0`） | **74.3** | 95.0 | 82.6 | 82.1 | 3:5 | 2.82 |
| Tree-RAG，gate 叶子读法（拆问题） | 65.7 | 95.0 | 87.0 | 79.5 | 4:8 | 3.44 |
| Tree-RAG，gate 叶子读法，LLM 预算 7 次 | 62.9 | 90.0 | 82.6 | 75.6 | 4:11 | 5.13 |
| Tree-RAG，best-first（证据搜索读法，全部动作） | 57.1 | 95.0 | 87.0 | 75.6 | 4:11 | 3.33 |
| Tree-RAG，MCTS | 54.3 | 95.0 | 87.0 | 74.4 | 4:12 | 3.24 |
| Tree-RAG，beam | 54.3 | 90.0 | 87.0 | 73.1 | 4:13 | 3.32 |
| 　消融：去掉 child / table / entity / section 动作 | 57.1 | 95.0 | 87.0 | 75.6 | 5:12 | 3.32 |

## 2. 结论

1. **Tree-RAG 的任何配置都没有在 dev 上胜过 V0.16 的参照方案**。最接近的是"gate 叶子读法 + VERIFY / 改写，不拆问题"：82.1 对 84.6，3:5，但 LLM 调用是参照的两倍多。所以按 held-out 纪律，这一轮不把任何 Tree-RAG 配置送去 held-out，推荐配置也不变。
2. **三棵树里最有用的是 Query Tree，但只对 reranker 读法有用。**
   - 用 reranker 读法时，拆问题让准确率从 61.5 升到 75.6（FinanceBench 从 31.4 升到 57.1）。FinanceBench 的问题常带"假设你是分析师……"这类长前缀，还要同时找多个数；拆成短的查找式子问题后，reranker 才能区分出相关单元。
   - 用 LLM 选读（gate）时，拆问题反而有害（82.1 → 79.5）。原因是每个子问题只分到一份预算（2 个子问题各约 1000 token），而 LLM 选读本来就能直接处理复合问题。
3. **在 Retrieval Search Tree 上，搜索策略的差别很小**：best-first 75.6、MCTS 74.4、beam 73.1。价值函数（MS MARCO 上训练的小 reranker）不够准时，搜索得再细也拿不到收益。这和 V0.16 的结论一致。
4. **Evidence Tree 的新动作（子节 / 表格 / 实体 / 节内检索）没有带来提升**：去掉它们后准确率不变（75.6）。在这些数据集上，相邻块、节标题和整页这几种展开已经够用。
5. **VERIFY 和改写查询有用，但不如答案层的 retry 划算**。参照方案只在答案明确说"证据不足"时才多查一次（约 1.3 次调用）；Tree-RAG 在检索阶段每个叶子都做 VERIFY，调用多了一倍，准确率却没有更高。

## 3. 局限与下一步

- 这三个 dev 集基本都是单文档、单跳、找数字的题，Tree-RAG 最擅长的多跳和跨文档问题没有覆盖到。要公平评估 Query Tree 和 Search Tree，需要专门的多跳题集。
- RAPTOR 摘要树已经实现并通过测试，但没有参加这轮评测：每份文档要调几十次 LLM，而且在已经有页级目录的 10-K 上，预期收益不大。
- 搜索树的价值函数可以换成更强的判别器，例如用 LLM 给少量节点打分，或者用金融领域的 reranker，再重新评估 MCTS。
- 在库里的端到端冒烟测试（Apple 2022 年报，5 道 finx 题）：`ask(retry=True)` 和 `search(strategy="best_first")` 都 5 题全对。Tree-RAG 每题 10～41 秒，`ask` 每题 7～8 秒。
