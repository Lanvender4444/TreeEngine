# V0.14 — Reasoned Retrieval：把 PageIndex 的推理用到检索这一步

V0.13 用 LLM 决定“候选池里读哪些、读多大”。V0.14 在此基础上，让 LLM 参与“候选池里有什么”。所有扩展都只向候选池或选读目录**添加**候选，不删除原有结果；阅读部分固定为 V0.13 的 `reason_node_sum`。

代码：`treeengine/reason/search.py`（库内流程 `reasoned_context`）、`benchmarks/reasoned.py`（基准用的分阶段并行版本）。切分沿用 V0.13 的 `--hash-split`，dev 和 test 不变。

## 1. 诊断（dev，不调用 LLM）

FinanceBench dev 35 题：7 题完全漏召回，8 题在池中但没进选读目录，20 题已在目录中。

- **漏召回的几乎都是报表题**：PPNE、quick ratio、DPO、毛利率、最大负债。正确证据在资产负债表、利润表等表格页上。问题用的是缩写或概念，表格里只有行项目和数字，BM25 和向量都对不上。
- **单路召回**：只用 FTS 为 66%，只用向量为 83%。
- **难度信号**：FTS 和向量各自前 10 名的重合度，在 FinanceBench 上能区分题目难易（证据进了目录的题平均 0.35，没进的 0.09），但在 longdoc 上方向相反。所以不用它做自动门控，改为让 LLM 自己判断是否需要更多检索。

## 2. 候选

| 模式 | 借鉴 PageIndex 的哪一点 | 做法 | 每题 LLM 调用 |
|---|---|---|---|
| `reason_x` | — | 查询扩展：LLM 把问题改写成 3 条“文档会用的说法”（报表名、行项目、缩写全称）。每条都走一遍混合检索，再与原结果做 RRF 融合 | 2 |
| `reason_toc` | 逐页目录 + LLM 推理定位 | 为文档生成逐页目录（每页一行：从该页开始的节标题，没有则取该页首行）。LLM 选 3 页，每页取 2 个最佳块，放进目录的预留位置 | 2 |
| `reason_search` | 迭代式阅读 | 选读器认为目录里没有所需信息时，给出补检索的查询，然后重新选择 | 约 1.1 |
| `reason_x_search` | — | 扩展，加上由 LLM 决定是否补检索 | 约 2.1 |
| `reason_plan` | 按难度选择检索方式 | 一次规划调用同时给出扩展查询，并判断这题要不要走目录路由，只对需要的题路由 | 约 2.2 |
| `reason_all` | — | 扩展、路由、补检索全开 | 3 |

## 5. 结论

1. **PageIndex 式的目录路由，作为附加通道是有效的。** `reason_toc` 是唯一在合并检验中显著的扩展（45:22，p=0.007），在三个题集上都没有变差。收益集中在 FinanceBench：证据进入选读目录的比例从 65% 提到 82%，@2000 的准确率从 48.3 提到 56.5，相对默认 auto（38.3）高 18 分。
   - 和 V0.13 中纯 PageIndex 式导航（FinanceBench 5.7）对比可以看出：同样是让 LLM 读目录选位置，单独使用会失败，作为检索之外的补充通道则有效。原因是召回仍由混合检索兜底，路由只负责补充“表格类、问法与原文用词对不上”的证据。
2. **查询扩展对报表题有效，但不通用。** 在 FinanceBench 上显著（31:16），在 multires2 上略负。multires2 的问题本来就用原文用词，改写后反而稀释了原查询。
3. **由 LLM 判断难度、自适应选择检索方式，这一轮还没有赢。**
   - `reason_x_search`（LLM 自己决定是否补检索）：test 上只有 5% 的题触发补检索，却在 multires2 上变差（6:16，p=0.05），比单纯扩展（12:15）还差。补检索真正触发得很少，所以更可能的原因是选读提示词里多了补检索选项，改变了选择行为。这只是推测，本轮没有专门检验。
   - `reason_plan`（LLM 判断是否需要目录路由）：test 上只对 11% 的题做了路由，比 dev 上的约 30% 更保守，因此拿到的路由收益比 `reason_toc` 少。
   - LLM 对“这题难不难、需不需要换检索方式”的判断还不够可靠。直接对所有题做路由，比让 LLM 判断要不要路由更好。
4. **dev 排名和 test 不一致。** dev 第一是 x_search，test 第一是 toc。dev 每个题集只有 20–35 题，噪声约 ±5 分，所以 dev 只适合淘汰明显差的方案，最终选择以 test 为准。

## 6. 决策

- 新增上下文策略：`reason_x`、`reason_toc`、`reason_search`、`reason_x_search`、`reason_plan`、`reason_all`，在库和基准中都可用。没有 LLM 时退回 auto；没有检索函数时退回 `reason_node_sum`。
- **推荐**：对长 PDF、财报、手册这类文档，问题措辞常与原文不同、证据常在表格里，使用 `context_policy="reason_toc"`。`"reason"` 仍等于 `reason_node_sum`，适合通用场景，成本更低。
- 默认值仍为 `auto`，不调用 LLM。默认检索路径与 V0.12 逐位一致。
- 成本：`reason_toc` 每题 2 次 LLM 调用，输入约 3.9k token，其中逐页目录约 1.8k。

## 7. 下一步

- **按文档类型自动启用路由**：把“带页码、页数多的 PDF 用 `reason_toc`，其余用 `reason_node_sum`”作为新假设。需要新的切分来检验，不能用本轮 test 回头调。
- **改进路由质量**：目前逐页目录只用节标题或页首行。可以试用页内表格标题（例如 “CONSOLIDATED BALANCE SHEETS”），或在入库时用 LLM 给每页生成一句摘要（PageIndex 的做法，有入库成本）。
- **让“是否需要路由”的判断更可靠**：例如给规划器看一份浓缩目录，而不是只看问题。
