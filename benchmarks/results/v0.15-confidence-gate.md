# V0.15 — Confidence Gate：多路候选、按置信度分流、合并式 PageIndex

## 思路

V0.14 之前，“候选从哪来、信号怎么合”和传统 RAG 没有本质区别：多路检索的结果按排名融合（RRF），再取前 N 个。V0.15 改成：

```text
候选生成（不调 LLM）  FTS │ 向量 │ （可选）文档树：每节按标题路径 BM25 + 子树向量中心排序，取最佳块
      ↓ 每个候选记录它在各路中的排名
置信度  逻辑回归 P(该候选是证据 | 各路排名, FTS 与向量是否都在前 10, 融合排名, 命中路数, 是否在某路排第一)
        只在 dev 上拟合（benchmarks/fit_gate.py → v0.15-gate-fit.json）
      ↓
分流    置信度 ≥ accept_tau → 直接读入（不经 LLM；最多 2 个，最多占一半预算）
        本题最高置信度 ≥ skip_tau → 整题不调 LLM，剩余预算按 auto 补满
        其余 → 一次 PageIndex 式 LLM 调用：低置信候选组成的目录 + 文档逐页目录，放在同一个提示里；
               LLM 可以选摘录、整节，或直接选某一页（"p57"）
```

代码：
- `treeengine/reason/gate.py`：置信度和分流；
- `RetrievalPolicy(fusion="gate")`：控制器中的多路生成和标注；
- `ReasonSpec.gate / outline`：分流后的阅读；
- 上下文策略 `gate`、`gate_fast`、`reason_outline`，以及用于扫描的 `gate@at=…;st=…;ol=…`。

## 1. 置信度校准（dev：FinanceBench / longdoc / multires2 的 dev 切分 + multires 全部，共 168 题、8249 个候选）

| 置信度 ≥ | 候选数 | 其中是证据的比例 |
|---|---|---|
| 0.3 | 183 | 60% |
| 0.5 | 114 | 68% |
| 0.7 | 52 | 79% |

拟合出的系数：FTS 排名倒数 2.13，向量排名倒数 1.14，两路都在前 10 0.74，树节点 0.14，其余都很小。**分数高的候选确实可信，但能达到高置信度的题不多**：本题最高置信度 ≥0.6 的题占 46%，≥0.7 的只占 31%。

### 合并检验与成本

| 配置 | 对 V0.13 node_sum | FinanceBench | longdoc | multires2 | 每题 LLM 调用 | 每题 LLM 输入 token |
|---|---|---|---|---|---|---|

直接对比：
- G-full 对 auto：100:18，p≈6e-15；
- G-full 对 V0.14 toc：45:31，p=0.14；
- G-full 对 outline：21:17，p=0.63；
- G-skip 对 G-full：11:16，p=0.44；
- 噪声对照：auto 第一轮对第二轮 5:7。

## 4. 结论

1. **按置信度分流，加上合并式 PageIndex，是目前最好的架构。** G-full 对 V0.13 为 50:16（p=3e-5），在三个题集上都没有输。FinanceBench @2000 达到 65.2，比 auto 的 43.0 高 22 分，比 V0.14 的 61.3 更高，而且每题 LLM 调用从 2 次降到 1 次。
2. **贡献最大的是“逐页目录并进选读调用”，即合并式 PageIndex。** outline 单独就有 44:12；去掉目录后，dev 上从正收益变成 22:33。高置信候选直接读入，在此基础上只增加了一点：G-full 对 outline 为 21:17，不显著。
3. **“高分直接用、低分才走 PageIndex”的省钱版本可用。** G-skip 让 27% 的题不调用 LLM，平均 0.73 次调用、2.8k token。它对 V0.13 仍有 50:20，和 G-full 的差异不显著（11:16）。阈值不能更低：dev 上约一半的题跳过 LLM 时（st=0.6），结果比 V0.13 更差。
4. **树节点作为第三路候选、混进排名时有害；权重越低越好，关掉最好。** 这与 rtree、NodeAnchor 的经验一致：树适合用来组织阅读单元、提供目录，不适合作为排名信号。所以 `node_source_weight` 默认为 0。

## 5. 推荐配置

```python
pol = RetrievalPolicy(fusion="gate", context_budget=2000, context_policy="gate")       # 推荐
pol = RetrievalPolicy(fusion="gate", context_budget=2000, context_policy="gate_fast")  # 约少 27% 的 LLM 调用
```

- `fusion="gate"` 只负责给候选加置信度标注，不改变 FTS + 向量的排序（树节点来源默认关闭）。
- 不用 `fusion="gate"` 时，候选没有置信度，`gate` 就等同于 `reason_outline`（test 上 44:12）。
- 没有 LLM 时，退回 auto。
- 默认仍是 `auto`，零 LLM。默认检索路径与 V0.12 逐位一致。

## 6. 局限

- test 切分在 V0.13、V0.14、V0.15 已经各用了一次。V0.15 的阈值、树节点权重和变体都只在 dev（含 multires）上确定，test 只运行最终的三个候选。但多轮之后，在 test 上挑最优版本仍有一定的选择偏差。下一轮应该用全新的留出集。
- 置信度模型只用了排名特征，没有用分数绝对值和题目特征；最高置信度很少超过 0.8，所以“完全跳过 LLM”能省的比例有限。
