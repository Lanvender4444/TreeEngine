# V0.13 — Reasoned Reading：把 PageIndex 的“推理式选读”接到混合检索后面

## 1. 动机：固定读法为什么到顶了

把端到端准确率拆成三项：

```text
A ≈ P(证据进入候选池) × κ(池中证据被读进上下文) × ρ(读到之后答对)
```

用 V0.12 FinanceBench 留出集的逐题数据（`context_coverage`、`candidate_recall`）估计：

| 读法 | P(池) | κ | ρ | 乘积 | 实测 |
|---|---|---|---|---|---|
| auto @1000 | 0.85 | 0.41 | 0.77 | 0.27 | 30.3 |
| raw @1000 | 0.85 | 0.58 | 0.53 | 0.26 | 28.7 |
| section600 @2000 | 0.85 | 0.55 | 0.74 | 0.35 | 40.7 |

- 固定读法（raw、auto、section600、adaptive、clustered）只是沿着一条 κ·ρ 近似守恒的曲线移动：读得广，κ 上升、ρ 下降；读得连贯，ρ 上升、κ 下降。
- 最大的损失项是 **κ**：FinanceBench @1000 有 29–43% 的题，证据已在 50 个候选里却没被读到，这些题的准确率约 10%。候选池漏召回只有 15%，读到但答错约 8%。
- 第一个正确块在候选池中的排名分布（FinanceBench）：前 1 / 5 / 10 / 20 / 50 名以内分别为 29% / 57% / 63% / 73% / 85%。前 20 个命中平均落在约 12 个不同节点里。

所以要提高 A，需要一个**看得懂内容的选择器**来提升 κ，同时对需要上下文的证据保持高 ρ。这正是 V0.12 Oracle Gap（8–11.5 分）无法用检索几何预测的原因：该读哪里的信息在内容里，不在位置分布里。

## 2. 借用 PageIndex 的哪一部分

PageIndex 的做法：用 LLM 给文档建一棵带摘要和页码范围的目录树，查询时让 LLM 读目录、推理出该打开哪些节点，不做切块，也不用向量。

| PageIndex 特性 | 对 TreeEngine 的意义 | 本版是否采用 |
|---|---|---|
| 推理式选择：LLM 看目录决定读哪里 | 直接作用于 κ（最大损失项） | **采用**：目录由检索候选池生成 |
| 以节点或页为阅读单元，不切碎 | 作用于 ρ（表头、单位、定义） | **采用**：可整节、整页读取 |
| LLM 摘要 | 让目录条目更好判断 | 部分采用：用已有的节点摘要（`reason_node_sum`） |
| 只靠目录导航，不做检索 | V0.6 实测在 longdoc 上比 hybrid 低 20 分（候选召回 50%）；FinanceBench 标题 F1 约 30% | 不采用，只作参照（`policy_tree`） |
| 多轮迭代阅读 | 成本成倍增加 | 第一轮先不做，视结果决定 |

## 3. 架构

```text
问题 ─► FTS + Vector ─► RRF ─► 候选池 50（不变，零 LLM）
                                   │
                                   ▼
                        RegionCatalog：按节（或页）把命中归组，
                        取前 10 个区域，每区最多 3 段摘录，
                        附标题路径、页码、整区 token 数（可选：节摘要）
                                   │
                                   ▼  一次 LLM 调用（约 2–3k 输入 token）
                        {"read": ["R2", "R1a", ...]}
                        R2 = 整区阅读（上限为预算的 70%，超出则围绕最佳摘录截取）
                        R1a = 摘录及其附近窗口（auto 窗口）
                                   │
                                   ▼
                        按 LLM 给出的顺序装入预算；剩余预算用池中其余命中补满
                        （回复无法解析时退化为 auto）
```

代码：`treeengine/reason/`（`catalog.py`、`reader.py`）。基准中的上下文模式：`reason_blocks`、`reason_node`、`reason_page`、`reason_node_sum`。

## 4. 候选架构与先验估计

| 编号 | 架构 | 作用于 | 先验判断 |
|---|---|---|---|
| A0 | auto（对照） | — | — |
| A1 | 纯 PageIndex：LLM 目录导航（`policy_tree`） | P(池) | 预期明显低于 A0（V0.6 实测 −20 分） |
| A2 | LLM 摘要作为检索信号 | P(池) | 上限仅为 15% 漏召回的一部分；V0.10 节点信号无贡献，暂不做 |
| A3 | `reason_blocks`：LLM 只挑摘录 | κ | 目录覆盖上限约 0.68；若 κ 达到 0.6–0.65，A ≈ 0.85 × 0.62 × 0.75 ≈ 0.40 |
| A4 | `reason_node`：可选整节 | κ、ρ | 节点切分碎、质量参差，整节的价值不确定 |
| A5 | `reason_page`：以页为单位，可选整页 | κ、ρ | FinanceBench 证据是页级，财务表格常在同一页带表头，先验最好 |
| A6 | `reason_node_sum`：A4 加节摘要 | κ | 目录更长，收益不确定 |
| A8 | auto / raw @3000、@4000 | — | 同成本对照：选择器多花的约 2.5k token 如果直接拿来多读，效果如何 |

## 5. 实验纪律

- 新 dev / test 切分：按 sha1(题号) 取模 4，dev 约占 25%（`--hash-split dev|test`），与任何结果无关。
- 第一轮只在 dev 上小规模跑（FinanceBench 35 题、longdoc 23 题、multires2 20 题）；只用 dev 选出进入下一轮的架构。
- 入选者在 test 上用全新的两轮 QA 验证，与 auto 和同成本对照做逐题配对符号检验。
- 默认检索路径不变（RRF、候选池 50、auto），确认与 V0.8 逐位一致。

## 6. 结果（详见 `benchmarks/results/v0.13-reasoned-reading.md`）

- dev 筛选：reason_node_sum、reason_node、reason_page 进入 test；reason_blocks 淘汰。纯 PageIndex 式导航在我们的树上明显更差（FinanceBench 5.7，longdoc 35）。
- test（251 题 × 2 轮），同预算对 auto 的逐题合并检验：reason_node_sum 84:23、reason_page 83:22、reason_node 78:23，p ≈ 1e-9 到 4e-8。三个题集、两档预算全部提升。
  - FinanceBench @1000：29.6 → 42.6（node_sum）/ 44.3（page）。
  - 证据覆盖率：39% → 约 55%。
- 同成本对照：@2000 的推理选读优于 auto @4000（node_sum 33:17，p=0.03）；@1000 不如 auto @3000。
- 增益最大的题型：
  - 财务指标计算题：17 → 45–47（@1000），整节读入后表头、单位、期间都齐了；
  - 跨节题和局部题：第二处证据被提到前面。

## 7. 使用

```python
from treeengine import TreeEngine, RetrievalPolicy

engine = TreeEngine("kb.db", llm=my_llm)          # 推理选读需要 LLM
pol = RetrievalPolicy(context_budget=2000, context_policy="reason")   # = reason_node_sum
res = engine.retrieve("What was FY2022 capex?", policy=pol)
res.context_spans      # LLM 选中的整节 / 摘录窗口，其余预算由候选池补满
res.trace              # "reasoned_reading": choice / whole / excerpts / fallback

engine.build_context(hits, 2000, policy="reason_page", question="...")  # 外部检索结果也可用
```

没有 LLM 或没有传问题时，自动退回 `auto`。默认策略仍是 `auto`。

## 8. V0.14：推理式检索（详见 `benchmarks/results/v0.14-reasoned-retrieval.md`）

V0.14 把同样的思路往前推了一步，用到检索上：让 LLM 参与“候选池里有什么”，只增加候选、不删除。

- `reason_toc`（逐页目录路由，PageIndex 式）是唯一在 test 上显著的扩展：对 node_sum 为 45:22，p=0.007。收益集中在 FinanceBench 的报表题。
- 纯目录导航失败，作为附加通道却有效。原因是召回仍由混合检索兜底，路由只补充那些“问法与原文用词对不上”的表格页。
- 让 LLM 判断题目难度、自行决定是否补检索或路由，这一轮还不如对所有题都做路由。

```python
pol = RetrievalPolicy(context_budget=2000, context_policy="reason_toc")   # 长 PDF / 财报
res = engine.retrieve("What is FY2018 net PPNE for 3M?", document_id=doc, policy=pol)
```
