# V0.16 — 参考路线落地：Reranker、表格感知解析、上下文索引、答案自检重试、提示词优化、Evidence Search（MCTS）

本文是 V0.16 新增模块的设计说明；实验结果见 `benchmarks/results/v0.16-routes.md`。

## 1. 总体结构

```text
                      ┌──────────── 解析 / 索引（离线） ────────────┐
PDF / Markdown ──▶ Evidence Builder ── pdf_tables：表格区域合成一块（Docling / DeepDoc 思路）
                                     └ index_title="context"：文档 | 章节路径 | 页标题（Contextual Retrieval）
                      └──────────────────────────────────────────────┘
                                      ▼
查询 ──▶ 候选生成（不调 LLM）  FTS │ 向量  （各自排名）
                                      ▼
         本地 Reranker（可选）  ce:<cross-encoder> │ colbert:<late-interaction>，对前 rerank_k 个块打分
                                      ▼
         置信度（逻辑回归，dev 拟合）  排名特征 + reranker 特征（inv_rerank、rerank_top1、rerank_z）
                                      ▼
   ┌─ context_policy ───────────────────────────────────────────────────────────────┐
   │ gate         高置信直接读入；其余一次 PageIndex 式选读（候选目录 + 逐页目录）     │
   │ gate+retry   答案声明“证据不足”时：排除已读块，重新检索、再选读、再回答           │
   │ search*      Evidence Search：reranker 作为节点价值函数的预算化搜索（无 LLM）      │
   │ search_loop  Evidence Search + 一次 LLM 充分性判断 + 改写查询（REWRITE_QUERY）    │
   └────────────────────────────────────────────────────────────────────────────────┘
```

默认路径（`auto`、`fusion="rrf"`、不开表格 / 上下文索引 / reranker）与 V0.12 逐位一致。

## 2. 各模块

### 2.1 本地 Reranker（`treeengine/retrieval/rerank.py`）
- `RetrievalPolicy(rerank="ce:Xenova/ms-marco-MiniLM-L-12-v2", rerank_k=30, rerank_order=False)`。
- 打分文本为 `index_title + 内容`；按 (模型, 查询, 文本) 缓存。
- 两种用法：
  - **作为置信度特征（推荐）**：不改排序，只让 gate 的置信度更准（`gate.RERANK_COEF` 按模型存 dev 拟合系数）；
  - `rerank_order=True`：按 reranker 重排前 k 个候选（传统两段式 RAG）。
- ColBERT 用 MaxSim（每个查询 token 取最大相似度后求和）。

### 2.2 表格感知 PDF 解析（`blocks/builder.py: table_regions / table_text`）
- 10-K 的 PDF 文本层把表格的每个单元格放在单独一行：解析出的行平均只有 69 个字符，中位数 7。按长度切块时，一张报表常被切到几个块里，表头、行标签和数值也会分开。
- `pdf_tables=True` 时：同一页内连续的短行（≥8 个单元格，数字占比 ≥30%）识别为表格区域，按“标签 + 数值”重建成行，合成一个 `block_type="table"` 的块（上限 `max_table_chars=3000`）。

### 2.3 上下文索引（`blocks/context.py`）
- `index_title="context"`：每个块的索引标题为“文档标题 | 章节路径 | 本页标题”。
- 本页标题跳过重复的页眉和通用行，比如 "Table of Contents"。
- 这个标题会进入 FTS、向量和 reranker，相当于 Anthropic Contextual Retrieval 的无 LLM 版本。

### 2.4 答案自检重试（`benchmarks/run_qa.py: +retry`；可用于任何上下文策略）
- 答案里如果出现“未提供 / 无法确定 / 证据不足”这类说法，就触发重试：
  1. 候选池 = 第一次的 50 个候选去掉已读块；
  2. 一次 LLM 调用，把问题改写成文档里的说法（2～3 条查询），用同一检索策略（FTS + 向量 + 置信度标注）检索，结果与剩余候选池融合；
  3. 用 `retry` 选读规格（区域摘要 + 逐页目录，不做高置信直接读入）再做一次 PageIndex 式选读；
  4. 只用新证据重新回答，并以第二次的答案为准。
- held-out 上的触发比例为 16～29%。每次触发多 2 次检索侧 LLM 调用和 1 次回答调用，所以平均每题检索侧 1.33～1.58 次。
- 目前实现在评测层（`run_qa.py`），还没有放进库的 `engine.retrieve` / `answer` 接口。

### 2.5 提示词优化（`benchmarks/optimize_prompt.py`，COPRO 式）
- 让 LLM 针对 dev 上的失败案例生成候选 guidance，在 dev 的两半上做 A/B，以证据覆盖率为指标。
- 最好的候选 0.794，默认 0.790，没有收益。默认提示词保留；`gd=` 参数保留，供以后使用。

### 2.6 Evidence Search（`treeengine/esearch/`）

把检索建模为状态空间上的预算化搜索：

| 概念 | 实现 |
|---|---|
| State | 已读证据单元、已覆盖的块、已用 token、剩余预算 |
| Actions | READ（候选窗口）/ READ_NEIGHBORS / READ_PARENT（节标题）/ READ_PAGE / REWRITE_QUERY（loop）/ STOP |
| Value（节点价值函数） | reranker 相关度（CE logit → sigmoid）；`prior>0` 时与检索置信度混合 |
| 优先级 | value × 新颖度 − λ × 新增 token / 预算 |
| Reward | 相关度（递减求和）+ 0.3 × 词项覆盖 − λ × 成本 − 0.2 × 冗余 |
| 策略 | `best_first`（优先队列）/ `beam`（证据集合为状态）/ `mcts`（UCT + rollout + 回传；最终沿访问最多的路径走，到叶子后接 best-first）|
| LLM 评估环 | `loop`：一次 LLM 判断是否可答；不可答时，用它给出的“缺失信息”作查询再检索，并继续搜索 |

上下文策略包括：
- `search`、`search_fill`、`search_beam`、`search_mcts`；
- `search_loop`；
- `search_prior`、`search_mcts_prior`；
- 参数写法如 `search@algo=mcts;iters=48;stop=0.2;prior=0.5`。

结论见结果文档：在本项目的数据上，**不调 LLM 的 Evidence Search 与 auto 大致持平，低于一次 LLM 选读（gate）**。原因有三：
- 财报问题需要整张报表，而 reranker 对“表格行 vs 问题”的相关度判断很弱；
- MCTS 的奖励只是 reranker 分数的代理，并不是“能否答对”；
- 搜索树在合理预算内只能展开两三层。

这套框架保留下来：价值函数可以换成更强的模型（例如经过金融领域微调的 reranker，或 LLM 打分）。
