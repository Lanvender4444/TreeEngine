# V0.10 — Retrieval Tree：一个层级检索空间，自适应阅读粒度

> TreeEngine 把词法、语义、结构和关系信号放进同一个层级检索空间，并根据问题动态决定应该读一个块、一个小节，还是更大的章节。

## 从「四个检索器」到「一棵树上的信号」

V0.6–V0.9 的检索流程：FTS、Vector、Tree、Graph 各自给出一份排名列表，最后做 RRF 融合。Tree 和 Graph 跟 FTS、Vector 平级，相当于两个外挂。

V0.10（`RetrievalPolicy(fusion="tree")`）的流程：

```text
query
  ├─ 词法 lexical    （块的 FTS）             ─┐
  ├─ 语义 semantic   （块的向量）              ├─→ 块激活（block activation）
  ├─ 关系 relational （Graph-lite 实体，横向） ─┘
  ├─ 节点词法 node lexical  （标题路径 + 开头文本的 BM25） ─┐
  └─ 节点语义 node semantic （query · 子树质心）            ├─→ 节点激活（node activation）
                                                            ┘
沿树向上传播：score(N) = 节点激活(N) + 子孙证据(N)
        ↓
从根开始做最优先遍历（best-first walk），在每个节点决定停在哪一层
        ↓
BlockAnchor 和 NodeAnchor 混在一个排名里 → ContextBuilder
```

**树是容器，FTS / Vector / Graph 是信号。** 它们不再各自产出结果列表，只负责在树上点亮块和节点。

## 各组成部分（`treeengine/rtree/`）

### 节点级索引（`index.py`，NodeIndex）

每个文档按需构建，在内存里缓存，用文档哈希检查是否过期。每个节点存：

- 层级关系：子节点、根节点、子树对应的块区间。
- 子树大小（估算 token 数）。
- `text`：标题路径（如「Item 7 > Liquidity」）加本节开头 300 字符，用于在文档内做节点 BM25。
- `centroid`：子树内块向量的均值。直接复用块检索已存的向量（新增 `VectorIndex.vectors()`），不额外调用 embedding。

不需要持久化：一个文档只有几百个节点，全部能从块、树和块向量推出来。

### 信号统一成排名质量

每个信号都只贡献 `w / (60 + rank)`，BM25、余弦、LLM 的原始分数从不相加。

- 块信号：FTS 和向量各取前 100 名，Graph-lite 按 `graph_weight` 给关联块加横向激活。
- 节点信号：每个文档的标题 BM25 和质心相似度各取前 20 名，权重是 `node_signal_weight`。

### 向上传播

子孙证据 = 子树中最强几个块的衰减和 `a₁ + a₂/2 + a₃/4`。

- 一节里有多个命中时，它的分数高于它最好的那一块（相当于「这一块被找到两次」）。
- 大节不能只靠块多取胜：只算前三名，后面的块不再加分。

### 最优先遍历与自适应停止（`search.py`）

从根开始，每次弹出分数最高的节点，按下面的规则处理：

| 情况 | 输出 |
|---|---|
| 装得进 `section_share × 预算`，并且 ≥2 个部分（子节点或自身块）含强证据 | **NodeAnchor**：读整节 |
| 没有块命中，但标题和质心两个信号都排进前 3，并且装得进 | **NodeAnchor**：仅凭树本身找到的节 |
| 其他情况 | 子节点入队；自身被命中的块作为 **BlockAnchor** 输出（保持细粒度） |
| 兄弟节点分数接近（≥85%），配置了 LLM，且 `agentic_level > 0` | 请 LLM 裁决，次数受 `max_llm_calls` 限制 |

**强证据**指本次查询激活值排名前 10 的块，按排名而不是按比例定义。排名质量很平，第 1 名和第 4 名相差不到 10%，所以「≥ 0.5 × 最强」这类比例门槛会让所有块都过线（开发时实测，见下）。

平的文档（只有一个节点）会自然退化为块检索。树错了，只会少几个整节单元，不影响块级证据。

NodeAnchor 交给 ContextBuilder 时带有 `read="section"` 和 `share`。ContextBuilder 以最强命中块为焦点，在节内最多读 `share × 本次构建的预算` 个 token；整节装得下就读整节。

## 和 PageIndex 式「LLM 看目录」的区别

PageIndex 那类做法是 LLM 一层层看目录、做选择，每一步都要调用 LLM。V0.9 的实测成本是每题约 3k token。

这里由确定性信号驱动遍历，LLM 只在兄弟节点分数接近、且策略允许时出场。默认 `agentic_level=0`，完全不调用 LLM。

## 同时提供：`context_policy="resolution"`（`context/resolution.py`）

这个上下文策略不改检索，只在 ContextBuilder 里按证据密度决定每个命中读窗口还是读整节，适用于任何检索结果（包括外部 retriever 的结果）。思路是：

1. 命中按排名质量计分，沿树向上汇总；
2. 没命中的块继承它所在、证据最密的上级节的密度；
3. 按排名顺序处理命中，用机会成本决定是否把窗口升级为整节。

开发过程的记录：

- 全局按「单位 token 价值」贪心：longdoc 上下文覆盖率下降 10–14 点（便宜的低排名单元挤掉了第一名）。
- 按排名顺序做局部比值比较：窗口永远赢，整节从来不会被选中。
- 最终采用机会成本判据：覆盖率与 auto 持平。

## 用法

```python
from treeengine import RetrievalPolicy
res = engine.retrieve(q, document_id=doc, policy=RetrievalPolicy(fusion="tree", context_budget=2000))
for a in res.anchors:
    print(a.kind, a.metadata.get("resolution"), a.metadata.get("node_title"), a.metadata.get("reason"))

# 只换阅读粒度，不换检索：
RetrievalPolicy(context_policy="resolution")
```

默认仍是 `fusion="rrf"` 和 `context_policy="auto"`，与 V0.8/V0.9 的输出逐位一致。
