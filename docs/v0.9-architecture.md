# V0.9 — Unified Anchors · Embeddable Integration · Graph-lite

三份计划的实现说明。默认行为不变：默认策略（FTS 1 / Vector 1 / Tree 0 / Graph 0）以及 tree 的 `blocks` 模式，检索输出与 V0.8 逐位一致（见末尾「回归」）。

## 1. Unified Retrieval / Anchor Architecture

所有检索器回答的是同一个问题：**这份文档的哪些位置值得读**。所以它们统一产出 `Anchor`：

| 检索器 | 类 | 产出 |
|---|---|---|
| 词法 FTS | `LexicalRetriever` | `BlockAnchor` |
| 语义 Vector | `SemanticAnchorRetriever` | `BlockAnchor` |
| 结构 Tree | `StructuralRetriever` / 控制器 tree 步 | `NodeAnchor`（整节值得读） |
| 扩展 Graph-lite | `GraphExpander` | `BlockAnchor`（`source="graph"`） |

```python
from treeengine import Anchor, BlockAnchor, NodeAnchor
from treeengine.retrieval import fuse_anchors

Anchor(kind="block" | "node", document_id, block_id, node_id, source, rank, score, metadata, evidence)
```

- **融合**：`fuse_anchors(lists, weights, k=60)` 按排名做加权 RRF（BM25、余弦、LLM 分数从不直接相加）。数学和并列顺序与 `EvidenceMerger.rrf` 完全相同，测试逐项验证过。权重 ≤ 0 的列表直接跳过。融合后 `metadata["retrieval_paths"]` 记录找到它的所有路径，`metadata["signals"]` 记录各路径排名。
- **NodeAnchor 是一等公民**：ContextBuilder 直接读这一节的连续正文（`own` 读本节，`subtree` 读本节加子节），不再先把节点转成「节点内 FTS 的几块」。旧行为保留为 `RetrievalPolicy(tree_anchor="blocks")`。
- **节点吸收所含证据**（`absorb_contained`）：纯 RRF 下，NodeAnchor 的 key 永远不会和块重合，只能拿到一项 tree 分数（权重 0.5 时相当于单路第 62 名），排在所有快路径块之后，预算内永远读不到；冒烟测试里 node 模式的上下文和不开 tree 一模一样。现在每个 NodeAnchor 接管本节内排名最高的快路径块：分数 = 该块的融合分 + 自己的 tree 分，等同于块被两条路径同时找到时获得的加分，该块从列表中移除，记为节点的 `focus_block_id`。ContextBuilder 围绕焦点块向两侧扩展，范围不超出本节（子树），而不是从本节开头读起；如果放不进预算，就退回只读焦点块。本节内没有快路径证据的节点保留自己的 tree 分。吸收必须在候选池截断（`candidate_pool`）**之前**做：节点只有一项 tree 分，先截断的话它在吸收前就被截掉了。第一轮 QA 正是这样，longdoc 前 20 题上 LLM 做了 60 次 READ，最后只有 2 题留下了 NodeAnchor；改成先吸收、再截断后是 16/20。
- `SearchResult.anchors` 是融合后的有序 anchor 列表；`SearchResult.evidence` 不变，仍是可引用的命中记录。三者的分工：Anchor 指明位置，Evidence 是可引用记录，ContextSpan 是模型实际要读的文本。
- `engine.ask()` 改为从 context span 作答，引用指向 span 的 anchor 节点、页码和 offset。旧行为：`EngineConfig(answer_context_tokens=None)`。

## 2. Embeddable Integration / Plugin Architecture

核心包不依赖任何框架。适配器都是薄层，全部调用同一个 `EngineService`（JSON 形态），本身不含检索逻辑。

```bash
pip install 'treeengine[mcp]'        # treeengine-mcp
pip install 'treeengine[server]'     # treeengine-server (FastAPI + uvicorn)
pip install 'treeengine[langchain]'  # TreeEngineRetriever
pip install llama-index-core         # TreeEngineLlamaRetriever（容器里没装，未实测）
```

### 外部检索结果 → 上下文重建

```python
spans = engine.build_context(
    [{"text": "...", "metadata": {"source": "/data/10k.pdf", "page": 41}}, ...],
    token_budget=2000, policy="auto",
)
```

外部命中（Pinecone / Qdrant / ES / 自研索引）按以下顺序映射回稳定 block：

1. `block_id`
2. 文档 + `start_offset`/`end_offset`（取重叠最多的 block）
3. 文档 + `text`（归一化子串）
4. 文档 + `page`
5. 只有 `text` 时：先 FTS，再做子串校验

文档的确定顺序：`document_id`，其次 `uri`/`source`（即 ingest 的路径），最后是调用方传入的默认值。映射不上的命中按原文透传，在预算内单独成段。输入可以是 dict、LangChain / LlamaIndex 对象、`ExternalHit`，也可以直接用 TreeEngine 自己的 Evidence 或 Anchor。

### LangChain / LlamaIndex

```python
from treeengine.integrations.langchain import TreeEngineRetriever
docs = TreeEngineRetriever(engine=engine, document_id=doc.id, context_budget=2000).invoke(q)
```

每个 `Document` 对应一个 ContextSpan。它的 metadata 包含 document / node / pages / block_ids / offsets / anchors / tokens。

### MCP 与 HTTP

- `treeengine-mcp --db x.db [--embedder fastembed:BAAI/bge-small-en-v1.5]`：提供 `list_documents`、`search`、`retrieve`、`build_context`，以及导航工具 `get_roots`、`get_children`、`get_ancestors`、`read_node`、`read_blocks`。兼容 mcp 2.x（`MCPServer`，已测）和 1.x（`FastMCP`，代码路径存在但未实测）。
- `treeengine-server --port 8765`：`POST /ingest|/search|/retrieve|/context`，`GET /documents`、`/documents/{id}/tree|roots`、`/nodes/{id}[/children|/ancestors|/blocks]`。未知的 policy 字段返回 422，找不到的资源返回 404。
- 两个服务都不需要 LLM：`retrieve` 用默认策略。只有调用方传入 `tree_weight > 0` 且服务启动时配置了 `TREEENGINE_LLM_*`，才会做 tree reasoning。
- 线程安全：MCP 和 HTTP 在工作线程里分发调用。为此 SQLite 连接改为 `check_same_thread=False`，并由 `EngineService` 持有一把锁，保证同一时刻只有一个调用。

## 3. Graph-lite：一跳实体扩展

- **抽取**（`graph/extract.py`）：确定性，不用模型或 LLM。类型包括 org（带公司后缀）、name（2–5 个大写词）、acronym、metric（固定财务指标表）、quoted（中文引号术语）。实体先做归一化（NFKC、小写、去公司后缀），通用词会被过滤。
- **索引**：schema v3 新增 `entities` 和 `entity_blocks` 两张表。开启方式有两种：ingest 时设 `EngineConfig(graph_index=True)`，或事后调用 `engine.build_graph_index()` 回填（幂等）。删除文档时其链接一并删除。
- **扩展**（`RetrievalPolicy(graph_weight>0)`）：
  - 取 fast path 排名前 `graph_seeds` 个 block 作种子。
  - 每个种子取最具体的 `graph_entities_per_seed` 个实体：specificity = log(1 + N/df) × 种子内出现次数；df < 2 或超过语料 2% 的实体跳过。
  - 每个实体取 `graph_blocks_per_entity` 个相关 block，同文档优先。
  - 总数不超过 `graph_max_blocks`。
  - 结果作为 `graph` 列表进入 RRF，本身不是主检索器。没建索引时只在 trace 里记一次跳过，不报错。
  - **只补充新块**：其他路径已经找到的块不会再进入 graph 列表。第一版没有这条限制，一个块同时出现在 FTS 和 graph 两个列表里会多拿一项 RRF 分，把 FTS 的第一名挤下去；longdoc 冒烟测试（30 题）中，graph_weight=0.25 时 recall@1 从 47.8 掉到 25.0。加上限制后 recall@1 不变，recall@10 从 73.3 升到 76.7。
- 默认 `graph_weight=0`，完全不参与。

## 回归

`scratchpad/v09/regress.py` 的检查范围：

- 7 个 fixture 文档，42 个查询 × {指定文档, 全库}
- 4 种策略：默认、FTS-only、tree fallback、tree full（`tree_anchor="blocks"`），外加旧的 `search()`

比较内容是 evidence（block / 节点 / 来源 / 分数）和 context span（block / token 数 / 文本）。比较时 ID 归一化为「文件@offset」。结果：V0.8 和 V0.9 的哈希完全相同。

测试：`tests/test_v09_anchors.py`（11）、`tests/test_v09_graph_lite.py`（4）、`tests/test_v09_integrations.py`（9）。全量 207 个通过；ruff 和 mypy 无问题。
