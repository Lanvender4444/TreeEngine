# V0.17 — Tree-RAG：Query Tree + Retrieval Search Tree + Evidence Tree

这一版对照《Tree》设计文档，把它说的三棵树做成库接口。目标是把检索从"一次 Top-K"变成"预算约束下的搜索与决策"：找出足以回答问题的、最小且质量最高的证据集合。

## 1. 接口

```python
from treeengine import TreeEngine, RetrievalPolicy

eng = TreeEngine("kb.db", llm=llm, embedder=embedder, use_vector=True)

# Tree-RAG：一次调用完成三棵树的搜索并回答
r = eng.search(
    question, document_id,
    strategy="best_first",              # best_first | beam | mcts
    budget={"max_steps": 12,            # READ 动作总数
            "max_llm_calls": 4,         # DECOMPOSE + VERIFY（回答那一次不计在内）
            "max_context_tokens": 2000},
    # 可选：policy=RetrievalPolicy.recommended()、decompose=True、
    #       actions="child,table,entity,section"、raptor=None（自动）、
    #       reranker="ce:..."，以及 SearchSpec 的字段（iters、c_uct、prior、window ...）
)
r.answer, r.citations              # 回答（综合所有子问题的证据）
r.query_tree                       # 实际检索的叶子问题
r.search_tree                      # SearchTree：RAGNode 组成的整棵树；r.render() 画成文本
r.context_spans, r.evidence        # 交给回答模型的证据
r.trace, r.stats                   # 动作轨迹；steps / pruned / retrieval_calls / llm_calls / tokens / latency

eng.search(question, document_id)  # 不传 strategy：和以前一样，只返回 Evidence[]

# 其他 V0.16 / V0.17 接口
eng.ask(question, policy=RetrievalPolicy.recommended(), retry=True)   # held-out 最优（V0.16）
eng.evidence_search(question, document_id, algo="mcts")              # 只做证据搜索（不分解、不回答）
eng.build_summary_tree(document_id)                                  # RAPTOR 摘要树（离线，调 LLM）
eng.build_graph_index()                                              # FOLLOW_ENTITY 需要 Graph-lite 索引
```

`r.render()` 的示例（MCTS 的节点还会显示访问次数 n 和平均奖励 q）：

```text
QUERY How did sales in region 1 and costs in plant 2 change?
├── SUBQUERY revenue sales region 1
│   ├── SEARCH_TEXT+VECTOR(revenue sales region 1) -> 50 candidates (fts 27, vector 26)
│   │   ├── [0.62] READ #1 READ_BLOCK 'Revenue fact 0: sales grew in region 0 ...'
│   │   │   ├── [0.16] READ #2 READ_NEIGHBORS '...'
│   │   │   ├── [0.16] PRUNED READ_CHILD '...'
│   │   │   └── … 1 more pruned
│   ├── VERIFY answerable=False coverage=0.50 missing='plant costs margin'
│   └── REWRITE_QUERY -> 'plant costs margin'
│       └── SEARCH_TEXT+VECTOR(plant costs margin) -> rewrite
├── SUBQUERY margin costs plant 2
│   └── ...
└── ANSWER Sales grew in region 1 [E1]; costs rose in plant 2 [E2].
```

## 2. 与设计文档的对应

| 设计文档 | 实现 |
|---|---|
| Document Tree | 解析得到的 节 → 子节 → 块，以及页；动作 READ_PARENT / READ_CHILD / READ_PAGE / SEARCH_IN_SECTION 沿着它走 |
| Query Tree（§10） | `DECOMPOSE`：一次 LLM 调用，把问题拆成至多 3 个查找式子问题（只需一次查找时不拆）。每个叶子各自跑一棵搜索树，token、步数、LLM 预算按叶子平分；最后综合回答 |
| Retrieval Search Tree（§6） | 每个叶子：SEARCH（FTS 和向量两路检索，按置信度融合；记录每个候选来自哪一路）→ 证据搜索 → VERIFY → REWRITE_QUERY → SEARCH …，每一步都是树上的一个节点 |
| Evidence Tree（§8、§11） | 每读一个单元，就生成它的扩展：READ_NEIGHBORS（前后块）、READ_PARENT（节标题）、READ_CHILD（各子节开头）、READ_PAGE（整页）、READ_TABLE（同页 / 相邻页的表格块）、FOLLOW_ENTITY（Graph-lite：与本单元共享最罕见实体的块）、SEARCH_IN_SECTION（所在节内做 BM25）；用价值函数决定先展开哪个，低价值的剪掉 |
| RAPTOR（§4、§9.2） | `build_summary_tree`：叶子是约 500 token 的连续块窗口；有 embedder 时按语义做 k-means 聚类，否则按顺序分组；每组由 LLM 写摘要，逐层向上，直到剩下不超过 fanout 个节点；存在 `raptor_nodes` 表里。搜索时摘要节点作为 READ_SUMMARY 单元：读它就把摘要放进上下文，它的子节点是下层摘要或叶子窗口 |
| Reranker 作为节点价值（§12） | 价值 = 0.5 × 交叉编码器相关度（sigmoid）+ 0.5 × 检索置信度先验（扩展出的单元继承父单元先验的 0.8 倍） |
| RRF → 初始节点先验（§13） | 置信度 gate（逻辑回归，特征包括 FTS / 向量 / reranker 的排名）给出每个候选的先验 |
| MCTS 四步（§15） | Selection（UCT）、Expansion（上面的动作）、Simulation（加噪贪心 rollout，按 reward 打分）、Backpropagation；最后沿访问最多的路径走，到叶子后接 best-first |
| Reward（§16） | 相关度（按排序递减求和）+ 0.3 × 词项覆盖 − λ × token 成本 − 0.2 × 冗余；VERIFY 由 LLM Judge 给出 answerable / coverage / missing，用来决定是否停止、改写什么查询 |
| 先 Best-first、再 Beam、最后 MCTS（§17） | `strategy=` 三种都支持 |
| 统一节点模型 RAGNode（§20） | `treerag.RAGNode`：id、parent、children、node_type、action、query、observation、document / section / block / page、relevance、prior、coverage、answerability、cost、read（阅读顺序）、visits、value |
| 动作空间第一版 / 第二版（§21） | SEARCH_TEXT+VECTOR、READ_BLOCK / PARENT / NEIGHBORS / CHILD / PAGE / TABLE、FOLLOW_ENTITY、SEARCH_IN_SECTION、REWRITE_QUERY、DECOMPOSE、VERIFY、STOP、READ_SUMMARY |
| 第三版（GRAPH_SEARCH / WEB / 跨文档） | 未做。跨文档：`document_id=None` 时检索本身就覆盖全库，但没有专门的跨文档动作 |
| 最终 API 与可视化（§24） | `engine.search(query, strategy=, budget=)` → `TreeRAGResult`；`render()` 输出文本树 |

## 3. 代码位置

- `treeengine/treerag/tree.py`：RAGNode、SearchTree（`render` / `to_dict` / `path` / `read_nodes`）。
- `treeengine/treerag/search.py`：`TreeRAG`（Query Tree → 每个叶子的搜索树 → 上下文重建 → 回答）。它接受任意检索函数，所以评测用的检索策略也能直接复用它。
- `treeengine/treerag/raptor.py`：RaptorIndex（构建、存储、读取）。
- `treeengine/esearch/core.py`：Evidence Search 的状态、动作、价值和三种策略。V0.17 加了 `actions`、`max_steps`、多轮 VERIFY（`loop_rounds`）、coverage 输出和 READ_SUMMARY。
- 评测：`run_qa --context "treerag[_beam|_mcts]@steps=;llm=;dec=;act=;raptor="`，回答和判分与其他读法走同一流程。

实验结果见 `benchmarks/results/v0.17-tree-rag.md`。
